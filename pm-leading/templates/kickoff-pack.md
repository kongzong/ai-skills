# 启动阶段模板包（Kickoff Pack）

> 项目立项时用。包含：项目章程、范围说明书、WBS。
> 给 AI 助手：不要把空模板丢给用户，**先问清项目信息，直接帮他填出初稿**，再让他修改。每个模板后附了新手示例。

---

## 模板 1：项目章程（一页纸）

```
# 项目章程：<项目名称>

## 一句话目标
<这个项目要解决什么问题，成功长什么样。要具体、可衡量>

## 背景 / 为什么做
<1–2 句：业务动因>

## 范围边界
### 本次要做（In Scope）
- <交付物/功能 1>
- <交付物/功能 2>
### 本次不做（Out of Scope）★别省这栏
- <明确排除的 1>
- <明确排除的 2>

## 关键干系人
| 角色 | 姓名 | 职责 |
|------|------|------|
| 项目发起人（出钱/拍板） | | |
| 甲方/客户（验收人） | | |
| 项目负责人（你） | | |
| 核心团队 | | |

## 里程碑与死线
| 里程碑 | 目标日期 | 说明 |
|--------|----------|------|
| | | |

## 约束与假设
- 约束：<预算/人力/技术红线/合规要求>
- 假设：<依赖的前提，如"甲方 X 日前提供数据">

## 我的权限
<能自行决定什么；什么需要上报>

## 确认
- 发起人/甲方确认：__________  日期：______
```

**新手示例（目标栏）**：
- ❌ "做一个稳定高效的订单系统"（无法验收）
- ✅ "3 个月内上线订单系统，支持日均 1 万单、峰值 500 并发，覆盖下单/支付/退款流程，替换现有手工 Excel 流程"

## 模板 2：范围说明书（Scope Statement）

```
# 范围说明书：<项目名称>

## 交付物清单（项目结束要交出什么）
| # | 交付物 | 验收方式（怎么算做完） |
|---|--------|------------------------|
| 1 | | |
| 2 | | |

## 明确不做（Out of Scope）★核心防线
- <被误以为在范围内、但本次不做的事>
- <留给二期的功能>

## 假设（Assumptions）
- <如：甲方在 X 日前提供测试账号与数据>

## 约束（Constraints）
- <技术栈限制 / 必须复用的系统 / 合规要求 / 预算上限>

## 范围变更规则
- 任何新增/修改需求，走《变更请求》流程，评估对进度/成本影响后由 <审批人> 决定。

## 确认
- 甲方确认：__________  日期：______
```

**填写要点**："验收方式"栏每条都要能回答"做到什么算通过"，写不出来的说明需求还没想清楚，要继续追问甲方。

## 模板 3：WBS（工作分解结构）

WBS 就是把大目标层层拆成 2–5 天能干完的小任务。可用缩进列表或表格。

**缩进列表式**：
```
1. <阶段/模块 A>
   1.1 <任务>（负责人 / 预估 X 天）
   1.2 <任务>（负责人 / 预估 X 天）
2. <阶段/模块 B>
   2.1 ...
...
N. 项目管理与收尾
   N.1 测试与联调
   N.2 部署上线
   N.3 文档编写
   N.4 甲方验收
```

**表格式**：
| WBS 编号 | 任务 | 负责人 | 预估工作量 | 依赖 | 完成标准(DoD) |
|----------|------|--------|-----------|------|---------------|
| 1.1 | | | | | |

**⚠️ 别漏这些"隐形工作"**（新手最常漏，占 30%+ 工作量）：
- [ ] 测试（单元/集成/联调）
- [ ] Code Review / 技术评审
- [ ] 部署、上线、灰度
- [ ] 数据迁移
- [ ] 文档（技术文档 + 用户手册）
- [ ] 甲方验收与修改
- [ ] 修 bug 的缓冲时间

**自查（100% 原则）**：把所有叶子任务加起来，是不是等于"项目全部工作"？有没有漏掉哪一块？
