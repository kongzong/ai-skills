# 困境应对 Playbook

> 给带项目时遇到具体麻烦的技术人。每条按「**症状 → 根因 → 立刻能做的动作 → 话术 → 方法论依据**」组织。
> 给 AI 助手：先定位用户最匹配的困境，**优先给能马上执行的动作和可直接照抄的话术**，再简短点出底层原因，避免长篇说教。

## 1. 需求/范围一直变，做不完

**症状**：功能越加越多，永远做不完；"就加个小功能"听了无数遍。

**根因**：项目启动时①没有书面范围说明书，②没有变更流程。于是任何人都能随口加需求，且没有成本。

**立刻能做的动作**：
1. **补一份范围说明书**（`templates/kickoff-pack.md`），重点写清 **Out of Scope（不做什么）**，发给甲方/老板确认。
2. **立即启用变更流程**：从今天起，任何新需求都要走"变更请求"（`templates/run-pack.md`），写明它会增加多少工期/成本。
3. 把"变更会影响交付时间"这件事**可视化**给决策者看——让加需求的人自己权衡。

**话术**（对提需求的人）：
> "这个需求可以做，不过它不在我们当初确认的范围里。加进来大概需要额外 X 天，会让上线推迟到 Y。您看是把它排进来（相应调整时间），还是放到二期？我发个变更单您确认下。"

**方法论依据**：范围管理（[scope.md](scope.md)）+ 铁律"变更走流程"。**范围蔓延的解药不是拒绝变更，而是让变更有成本、可见、可决策。**

## 2. 老板/甲方天天催进度，我不知道怎么答

**症状**：一被问进度就心虚，只能答"快了""在做了"，对方越问越紧。

**根因**：没有**主动的、基于事实的**汇报节奏。你不说，他只能猜，猜不到就来催。

**立刻能做的动作**：
1. **建立每周书面周报**（`templates/run-pack.md` → 状态周报），主动推送，把"被动被催"变成"主动告知"。
2. 汇报**用事实不用感觉**：完成了哪几个里程碑 / WBS 任务完成 X 项共 Y 项 / 风险有无新增。
3. 有延误风险要**提前预警**，别等出事——早说是负责，晚说是背锅。

**话术**（周报开头）：
> "本周进展：完成 A、B；进行中 C（预计周三完成）。整体进度符合计划 / 有 X 天风险（原因+应对）。需要您协调：D。"

**方法论依据**：沟通管理（[communication.md](communication.md)）——用数据说话。**主动汇报的人掌握节奏，被动挨问的人永远被动。**

<a id="3"></a>
## 3. 快到期了才发现做不完

**症状**：临近死线，突然意识到剩下的活干不完。

**根因**：没有里程碑和进度跟踪，问题一直被"应该快好了"掩盖，到最后才暴露。

**立刻能做的动作**（止血优先）：
1. **立刻算清真实差距**：还剩多少工作量、还有多少时间、缺口多大。别再自欺。
2. **马上上报，给方案不给情绪**。晚报一天，损失大一分。
3. 拿出**取舍选项**让决策者选，通常是这三选一（或组合）：
   - **砍范围**：哪些功能可以砍到二期？（保核心）
   - **加资源**：能不能加人/加班？（注意加人未必更快）
   - **延期**：推迟多久能保质量？
4. 事后复盘：为什么这么晚才发现？——补上里程碑和周跟踪。

**话术**（上报时）：
> "有个必须现在同步的情况：按当前进度，X 功能会延期约 N 天。我准备了三个方案：①砍掉 P2 功能保准时上线；②加 1 人可能追回 M 天；③整体延期 N 天保完整。各有利弊，想请您拍板方向。"

**方法论依据**：进度管理（[schedule.md](schedule.md)）+ 范围管理。**范围、时间、资源是铁三角，动一个必然影响另外两个——出问题时就在这三者间做交易。**

<a id="4"></a>
## 4. 估算不准，工期总是拖

**症状**：说好三天的活干了一周，几乎每次都低估。

**根因**：①只估了"写代码"的时间，漏了测试/联调/评审/改 bug/等依赖/开会；②用了"顺利情况"估算，没留缓冲；③任务太大估不准。

**立刻能做的动作**：
1. **把任务拆更细**（2–5 天粒度），细任务估得准。
2. 估算时**显式加上隐形工作**：测试、联调、Code Review、修 bug、部署、写文档、等别人。
3. 用**三点估算**给不确定任务：`(乐观 + 4×最可能 + 悲观) / 6`，比拍脑袋一个数靠谱。
4. 整体留 **15–20% 缓冲**，别把日程排满。
5. 记录"估算 vs 实际"，几轮后你就知道自己惯性低估多少，乘个系数。

**方法论依据**：进度管理（[schedule.md](schedule.md)）。**工程师的乐观是估算的天敌——你估的是"代码写完"，项目要的是"能上线验收"。**

<a id="5"></a>
## 5. 供应商/外包/兄弟团队不配合、拖延

**症状**：依赖对方的接口/资源/交付，对方一拖再拖，你的进度被卡死。

**根因**：没有书面的责任约定和验收标准，也没把这条外部依赖当风险管起来。

**立刻能做的动作**：
1. **把依赖白纸黑字化**：要什么、什么标准、什么时间点交，发给对方 + 抄送双方上级确认。
2. **设检查点**：不要等最终交付，约定中间里程碑，早发现拖延。
3. 把这条依赖**登记为风险**（`templates/run-pack.md`），并**准备 Plan B**（能否先用 mock/桩、能否找替代）。
4. 拖延一旦影响关键路径，**立刻升级**给双方管理层，用事实说话。

**话术**（升级时，对双方老板）：
> "同步一个依赖风险：我们需要 X 团队的 A 在 3 号前交付，目前已延期，会直接导致我们的里程碑 B 推迟。想请两边协调一下优先级，或者我们启用备用方案 C（但有 D 影响）。"

**方法论依据**：采购管理（[procurement.md](procurement.md)）+ 风险管理。**对外部依赖，口头承诺 = 没有承诺；要书面、要检查点、要 Plan B。**

<a id="6"></a>
## 6. 团队成员不出活 / 摸鱼 / 各干各的

**症状**：分了任务但进展慢，不知道每个人在干嘛，到 deadline 才发现没做。

**根因**：任务不清晰（不知道做到什么算完）、没有可见的进度、缺少日常同步。

**立刻能做的动作**：
1. **每个任务定义清楚"完成标准"（DoD）**：做到什么程度算做完，别只给个标题。
2. **上看板**（哪怕最简单的待办/进行中/完成），让每个人的活和进度**可见**。
3. **每日站会 15 分钟**：昨天做了什么、今天做什么、卡在哪——不是汇报给你，是团队互相同步、暴露阻塞。
4. 对持续不出活的人，**单独 1v1** 弄清是能力问题、任务不清、还是有阻塞，对症解决而不是笼统施压。

**方法论依据**：人力资源管理（[hr.md](hr.md)）+ 沟通管理。**"看不见的工作"最容易失控——让工作可见，问题会自己浮出来。**

<a id="7"></a>
## 7. 跨部门推不动，没人鸟我

**症状**：需要别的部门配合，但你没有对他们的管辖权，请求石沉大海。

**根因**：技术负责人往往有责无权。靠个人面子推事，推不动很正常。

**立刻能做的动作**：
1. **借势**：让你的老板/项目发起人出面背书，把"你个人的请求"变成"项目的正式需求"。
2. **书面 + 明确**：写清要什么、为什么（对整体目标的影响）、什么时候要、不给会怎样，抄送相关领导。
3. **让对方好办事**：把请求拆到最小、给清楚上下文，降低对方的配合成本。
4. **建立干系人台账**：谁对项目有影响、谁能帮你、谁可能挡路，提前经营关系而不是临时求人。

**方法论依据**：沟通/干系人管理（[communication.md](communication.md)）+ 整合管理。**跨部门协作靠的是"势"和"流程"，不是靠你一个人的人情。**

<a id="8"></a>
## 8. 需求方说不清要什么

**症状**：甲方/业务只会说"你懂的""先做个大概看看"，做出来又说不对。

**根因**：需求没有被"逼"到可测量、可验收的程度。

**立刻能做的动作**：
1. **用产出物逼近需求**：给原型/草图/示例，让对方在具体东西上说"对/不对"，比问"你要什么"有效得多。
2. **把每条需求写成可验收的样子**：给出"输入→预期结果"，让对方确认。写不出验收标准的需求 = 还没想清楚。
3. **小步演示**：别憋大招，每个里程碑给对方看一次，早对齐早纠偏。
4. 需求确认后**书面留痕**，作为后续变更的基线。

**方法论依据**：范围管理（[scope.md](scope.md)）——制定业务验收基准。**模糊的需求不能靠猜，要靠"可确认的具体物"去逼清楚。**

<a id="9"></a>
## 9. 风险突然爆了 / 出了大事故

**症状**：线上事故、关键人离职、核心方案被推翻……项目被打乱。

**立刻能做的动作**（按顺序）：
1. **先止血，再复盘**：第一时间控制影响面（回滚、降级、隔离），别急着追责。
2. **透明上报**：向上如实同步现状、影响、正在采取的措施和预计恢复时间。**藏问题会让事情烂得更快。**
3. **拉相关人一起定方案**，明确谁负责什么、什么时候检查。
4. 稳定后做**无指责复盘（Blameless Postmortem）**：找系统原因不找背锅侠，把改进项落成行动。
5. 更新风险登记册，把这次的教训变成以后的预防。

**话术**（上报事故）：
> "报告一个情况：X 发生了，目前影响 Y。我们已采取 Z 止血，预计 N 小时内恢复。根因还在定位，稍后给完整复盘。需要的支持：……"

**方法论依据**：风险管理（[risk.md](risk.md)）。**危机中，透明和速度比完美更重要；事后，机制改进比追责更重要。**

<a id="10"></a>
## 10. 验收时甲方说"这不是我要的"

**症状**：辛苦做完，验收却过不了，甲方说的和你理解的不一样。

**根因**：没有事先书面约定的验收标准，双方对"做完"的定义不同。

**立刻能做的动作**（补救）：
1. **翻出当初确认的范围/需求文档**逐条对照——哪些是范围内已交付、哪些是对方新增的期望。
2. 属于**范围内没做好**的：诚恳认领，给修复计划。
3. 属于**范围外新期望**的：走变更流程，作为二期或追加。
4. **划清楚"完成了什么" vs "还想要什么"**，分开处理，别混在一起背锅。

**根治（下次一定）**：项目一开始就和甲方**共同制定、书面确认验收标准**（`templates/closeout-pack.md` → 验收清单），每项写清"怎么算通过"。

**方法论依据**：范围管理"业务验收基准" + 铁律"关键决策白纸黑字"。**验收纠纷 99% 源于开工时没定验收标准——标准要在开始时定，不是结束时吵。**

<a id="11"></a>
## 11. 我又要写代码又要管项目，忙不过来

**症状**：白天开会协调、答疑、写文档，晚上才能写代码，两头都做不好。

**根因**：技术负责人的常见陷阱——没意识到"管理"本身就是一份全职工作量。

**立刻能做的动作**：
1. **接受角色转变**：你的产出不再只是代码，而是"让整个项目产出"。**适当从关键路径的编码任务上退出来。**
2. **授权**：把能分出去的技术任务交给团队，你保留架构决策和攻坚，而不是所有代码都自己写。
3. **保护你的时间**：把沟通/会议集中到固定时段（如上午），留出整块时间做需要专注的事。
4. 如果项目确实大，向上申请**专职 PM 支持**或减少你的编码承诺。

**方法论依据**：人力资源/整合管理。**你最大的价值从"写最好的代码"变成了"让团队交付成功"——抓不住这个转变，两头都会塌。**

<a id="12"></a>
## 12. 老板临时塞新需求，还不给加时间

**症状**：项目进行中，老板说"顺便把这个也做了"，但死线不变。

**立刻能做的动作**：
1. **不要默默接受**——默默接受 = 你独自承担超载和延期风险。
2. **把取舍摆到台面上**：新需求要占用资源，那么原有的什么要让路？让老板做这个交换决定，而不是你硬扛。
3. 用**范围/进度铁三角**沟通：范围加了，时间或资源必须动一个。

**话术**：
> "这个新需求没问题，我可以排进来。不过团队产能是固定的，加了它，要么把原计划里的 X 往后放，要么上线推迟约 N 天。您看优先级怎么排？我按您定的调整计划。"

**方法论依据**：范围 + 进度管理，铁三角。**新手容易"老板说啥都硬接"，结果自己爆炸还背锅；正确做法是把交换成本透明地交还给决策者。**

<a id="13"></a>
## 13. 项目一团乱，我半路接手烂摊子

**症状**：接手一个已经在跑、但没人说得清状态的项目。

**立刻能做的动作**（先盘清再动手）：
1. **盘家底**：现在做到哪了？范围是什么？谁在干什么？有哪些没还的"债"（技术债/承诺）？
2. **找真相**：分别找团队成员、甲方、前任负责人聊，交叉验证真实状态（各方说法往往不一致）。
3. **补最关键的两样**：如果没有范围说明书和进度基线，先补这两个，其它慢慢来。
4. **重设期望**：基于盘出来的真实状态，重新和老板/甲方对齐"现实的目标和时间"，别背前任的锅还硬扛不现实的承诺。
5. 之后按 [`quickstart-kickoff.md`](quickstart-kickoff.md) 的框架把缺失的环节逐步补齐。

**方法论依据**：整合管理 + 范围管理。**接烂摊子第一要务是"看清现状"，第二是"重设现实的期望"，切忌一上来就埋头干。**

<a id="14"></a>
## 14. 需求方反复推翻已确认的方案

**症状**：方案、原型、甚至接口都确认过了，过两天对方说"还是按之前那个思路吧"，或换个人来说另一套，你返工到崩溃。

**根因**：确认时没有**把决策固化成书面记录并让有权的人签字**。口头"行"只代表当时那个人的临时意见，不等于组织承诺。

**立刻能做的动作**：
1. **每次关键确认都留书面痕迹**：评审纪要 / 邮件 / 文档批注，写明"确认内容 + 确认人 + 日期"，发出去让对方回复确认。
2. **确认对象要对**：让业务负责人（王总这种拍板的人）而不是随便一个对接人来确认，避免"他确认的他领导不认"。
3. **被推翻时，翻旧账讲成本**："这个我们在 9/10 确认过（附记录），推翻意味着返工 X 天、影响 Y 里程碑，您确定要改吗？"——把反复的成本显性化。
4. **设"冻结点"**：明确告知"设计 9/15 冻结，之后改动一律走变更流程加时间"，给反复画条线。

**话术**（确认时）：
> "这是按今天讨论敲定的方案（附原型+要点），麻烦您回复确认，我就按这个往下做，9/15 设计冻结后改动要走变更流程。确认后我会存档，方便后续对齐。"

**方法论依据**：范围管理"业务验收基准" + 铁律"关键决策白纸黑字"。**反复推翻的解药不是更努力，而是把每次确认变成对方赖不掉的书面承诺。**

<a id="15"></a>
## 15. 关键成员突然离职 / 被借调

**症状**：核心开发要离职，或被大促/其他项目借调走，关键路径瞬间断档。

**根因**：知识只在一个人脑子里（Bus Factor = 1），没有备份和交接机制。

**立刻能做的动作**：
1. **立刻盘"他一个人掌握的东西"**：哪些模块、哪些接口、哪些坑只有他清楚，列清单优先转移。
2. **建文档 + 结对**：让他用 1–2 周把核心逻辑写成文档，并和替补结对讲一遍，**交接以"别人能接手"为完成标准**。
3. **保护关键路径**：若被借调，申请"关键路径人员保护"——借调需你（PM）批准，或错峰借调不撞里程碑。
4. **重排期并上报**：关键路径断档必然影响时间，用 [`playbook.md`](playbook.md) #3 的方式上报取舍，别硬扛。
5. **长期**：WBS 任务尽量两人能接，避免单点依赖（这是下次立项就要立的规矩）。

**话术**（对老板）：
> "核心开发小张下周离职，他手上的订单状态机目前只有他清楚，是 M2 关键路径。我需要这周让他和后端B 结对交接+写文档，并申请这段时间不被借调，否则 M2 有 5 天风险。"

**方法论依据**：人力资源管理（[hr.md](hr.md)）+ 风险管理（单点故障是 R 级风险）。**一个人能扛事是好事，但"只有他扛得了"是项目最大的隐患。**

<a id="16"></a>
## 16. 技术债 vs 新需求，先还债还是先交功能？

**症状**：老板只要新功能冲业绩，但系统越改越慢、bug 越多；你想还技术债，又怕被说"不产出"。

**根因**：技术债和业务价值都被你当成"非此即彼"，没转化成老板能懂的语言和可视的成本。

**立刻能做的动作**：
1. **别用"技术债"这种词跟老板谈**，用"交付速度"谈：把技术债翻译成"不做的话，下个需求要多花 N 天 / 线上故障概率升 M%"。
2. **切小块还债，混进正常迭代**：不要申请"停两周专门重构"，而是每个迭代固定留 10–15% 额度做必要重构，老板无感、债务可控。
3. **用数据立证**：记录"重构前这个功能改一次 3 天，重构后 1 天"，用对比证明还债不是浪费。
4. **设定底线**：出现"不改就会线上故障 / 无法扩容"的债，直接列为风险（[risk.md](risk.md)），必须排期，不是可选项。

**话术**（对老板）：
> "订单状态机这块历史债不处理，这次加新功能要多花 5 天，而且上线后故障风险高。我打算每迭代抽 10% 时间慢慢还，不影响新功能交付节奏，但能保住交付速度。涉及扩容的这部分债我列为必须做的，其余慢慢来。"

**方法论依据**：整合管理（在业务价值与技术健康间找平衡）+ 风险管理。**技术债不是"该不该还"，而是"用老板听得懂的速度和故障语言，把它变成可排期的投资"。**

<a id="17"></a>
## 17. 业务方不回消息、不参加评审

**症状**：需求确认、评审、UAT 找业务方，石沉大海；等上线了他们才冒出来挑刺。

**根因**：业务方没有"必须参与"的约束，你也没有把"不参与 = 自己承担后果"说清楚。

**立刻能做的动作**：
1. **把参与写进章程/范围说明书**：明确"业务方需在 X 日内确认需求、参加里程碑评审"，作为项目基线的一部分。
2. **设 Deadline + 默认同意**："需求确认截止到周五，超时未回复视为按当前方案执行"——用默认机制逼出决策，而不是无限等。
3. **升级而非死等**：超时未回，抄送其上级 + 发起人（王总），说明"卡在这会影响整体进度"，借势推动。
4. **降低参与成本**：别让人家读 20 页文档，给一页摘要 + 几个选择题，让确认变容易。

**话术**（跟进）：
> "王总，订单状态机方案需业务方在周五前确认（附一页摘要+3 个选择点）。如逾期未确认，我将按当前方案推进并视为认可，以免阻塞 M2。如需协调业务方时间，请您帮忙推动。"

**方法论依据**：沟通/干系人管理（[communication.md](communication.md)）+ 铁律"关键决策白纸黑字"。**业务方不回消息，多半是你没给他们"不回的代价"——把代价写进基线，Deadline 才管用。**

## 18. 上线了却没人兜底，线上问题频发

**症状**：项目上线算完，结果半夜告警、线上 bug 没人管，业务骂声一片，你又回去当救火队长。

**根因**：把"上线"当终点，没规划"上线后的运营与值守"，责任没交接给运维/SRE。

**立刻能做的动作**：
1. **上线前就定好值守**：在切流方案里写明"上线首周 X 人 on-call、SRE 值守、告警群"，别等出了问题再找人。
2. **交接运维**：把监控看板、运维手册、常见故障处理 SOP 交给 SRE/运维，并做一次交接评审（[closeout-pack.md](../templates/closeout-pack.md) 验收清单含此项）。
3. **建响应机制**：明确 P0/P1 的响应时限和升级路径（谁接、报谁、多久恢复），写进运维手册。
4. **设稳定运行期**：上线后观察 1–2 周无 P0/P1 才算真正交付，期间你仍要在，但逐步把 on-call 转给运维。

**话术**（上线前对齐）：
> "切流 11/15 启动，我建议首周后端B + SRE 双人 on-call，告警直接进群，P0 响应 < 15 分钟。运维手册和 SOP 我 11/10 前交付并评审。稳定 1 周后 on-call 转 SRE。"

**方法论依据**：质量管理（[quality.md](quality.md) 运维交接）+ 结束管理（上线≠结束，要交接兜底）。**把"上线"当成"交付给用户"，而不是"甩给运维"——亲手把兜底机制立起来，才不算半途而废。**

## 通用心法（所有困境背后的共性）

- **80% 的项目困境，根子都在"启动时没做好"**：没定范围、没立变更规则、没约定沟通和验收标准。遇到困难时，往往是在补启动阶段欠的债。
- **坏消息要趁早、主动、带方案地说**：晚说、被动说、只说问题不给方案，是新手负责人最容易踩的三个雷。
- **把决策交换成本还给决策者**：范围/时间/资源三选一的取舍，是老板/甲方的决定，不是你一个人硬扛的。你的职责是把选项和影响讲清楚。
